# /meeting-close — 미팅 후 정리

대상: `$ARGUMENTS` (비어 있으면 `meetings/`에서 가장 최근 폴더)

## 순서

1. 대상 폴더의 `notes.docx`를 `tools/office-read.ps1`로 읽는다(`notes.txt`나 `notes.md`면 그대로 읽는다). 없거나 비어 있으면 멈추고 메모를 먼저 쓰도록 안내한다. `brief.docx`가 있으면 함께 읽는다.
2. 메모가 모호한 부분(누가, 언제까지, 무엇을, 결정인지 제안인지)은 추측하지 말고 한 번에 모아서 묻는다. 질문은 summary의 결정·할 일·기한을 바꾸는 것만, 5개 이내로 묻는다. 나머지는 묻지 않고 `미입력`으로 둔다.
3. `templates/meeting-summary.md`의 구조로 Word 문서 `summary.docx`를 만든다(`CLAUDE.md`의 "Word 만들기". 첫 문단에 `예시 — 실습용 가상 자료입니다.`. 같은 파일이 이미 있으면 덮어쓰지 말고 묻는다. 만든 뒤 다시 읽어 확인한다).
   - **결정:** 메모에 "~하기로 함", "~으로 정함"처럼 정해졌다고 적혀 있거나, 사용자가 결정이라고 확인한 것만 쓴다. "~하면 좋겠다고 하심", "~할 것" 같은 제안과 지시는 **피드백**에 두고, 결정인지 애매하면 2단계에서 묻는다. 이유가 메모에 없으면 `메모에 없음`.
   - **피드백:** 지도교수나 동료가 준 의견. 말한 사람을 알 수 있으면 적는다.
   - **할 일:** 무엇을, 어느 프로젝트에서, 언제까지. 기한이 메모에 없으면 `미정`.
   - **기다리는 일:** 다른 사람에게서 받아야 할 것.
   - **미해결 질문:** 메모에 물음표로 남은 것, 결론이 나지 않은 것, 사용자가 답에서 미정이라고 한 것. Claude가 새로 떠올린 질문은 넣지 않는다. `brief.docx`의 질문은 아래 "준비했지만 다루지 못한 질문"에만 둔다.
   - **준비했지만 다루지 못한 질문:** `brief.docx`의 질문 중 메모에 답이 없는 것.
4. 갱신을 제안하고, 승인받은 것만 반영한다.
   - **`todo.md`:** 추가하거나 바꿀 항목. 출처 칸에 `<날짜> <종류>`를 적는다. 상태는 `CLAUDE.md`의 상태 용어를 쓰고, 기한보다 늦게 끝난 항목은 지연을 표시한다.
   - **`projects/*/status.md`, `plan.md`, `roadmap.md`:** 결정 때문에 바뀌는 내용이 있으면 제안한다. `status.md`를 고치기 전에는 history에 복사한다.

## 주의

- `notes.docx`는 고치지 않는다.
- 메모에 없는 결정, 할 일, 기한을 만들지 않는다.
